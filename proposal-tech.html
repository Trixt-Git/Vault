TO:AI Champions Club & Technical Team FROM:Vault Project RE:Suggested tools, system setup, and how each piece fits together

Plain, reliable software. Python and SQL carry almost all of it. Vault runs alongside your existing systems like an assistant looking over a shoulder: it reads copies of past jobs to help draft new quotes, but it can never edit, overwrite, or delete anything in your live shop software. Every tool below is a practical suggestion, and Discovery decides what we actually use.

1. THE STACK AT A GLANCE

Part Suggested Tool What It Does & Why
Language Python 3.12+, SQL Standard, dependable code. Easy to read, maintain, and hire for.
Models Local (Ollama) or Google Gemini API On-premise execution keeps customer data inside our network; Google Gemini API under commercial terms (never trains on customer data) as managed fallback.
Web Service FastAPI Handles requests quickly and streams answers onto the screen as they are written.
First Screen Streamlit or a plain web page A simple, clean screen so the team can try it out immediately without building a complex UI first.
Database PostgreSQL (with pgvector) One database for everything: past quotes, approval history, text search, and meaning-based search.
Input Checks Pydantic v2 Checks every piece of data before running it, catching typos and bad inputs right away.
Data Tables SQLAlchemy 2.0 & Alembic Keeps database tables organized and tracks table updates cleanly as we add features.
Workflow LangGraph (Postgres) Tracks where a job is, pauses safely for a person to approve, and picks up right where it left off.
Testing pytest, Ragas, Langfuse A scorecard that runs after every change so accuracy, speed, and cost stay on target.
Shipping Docker, GitHub Actions Packages the app in a clean container so it runs the exact same way on any server.
Login Company login (Microsoft or Google) Uses the work account staff already have, so there are no extra passwords to manage.
Shop Systems Read-only copies from your print software Vault only reads past job copies; it never touches or changes your live shop software.

3. WHY WE PICKED THESE TOOLS

Part What We Picked Alternatives Why (In Plain English)
Database PostgreSQL + pgvector Pinecone, Qdrant One database instead of two: Keeping past jobs and search data together means simpler backups, fewer moving parts, and no extra monthly subscriptions.
Search Text search + meaning search Meaning search only Catches what either misses alone: Plain text search finds exact job numbers ("J-2188") and paper weights ("80 lb cover"). Meaning search finds similar descriptions. Using both prevents missed jobs.
Workflow LangGraph (Postgres) Autonomous AI swarms A clear, predictable path: Steps run in order and stop at every human approval point. It waits patiently for you instead of letting AI run in uncontrolled loops.
Input Checks Pydantic v2 Unchecked dictionaries Catches bad data before it runs: If an email has weird formatting or missing fields, it catches the problem right away before the rest of the code touches it.
Login Company login (Microsoft / Google) Custom passwords Uses normal work accounts: Staff use their normal work accounts. When someone leaves the company, turning off their work account turns off Vault automatically.

4. THE 9-STAGE DELIVERY PLAN

STAGE 0DISCOVERY & BASELINE

Measure the task with a stopwatch and set the target.

BUILD
No software. A time log tracking 20–50 real customer requests from receipt to invoice. A map of shadow spreadsheets and handoffs.
USE
Excel / Google Sheets for time tracking. Miro / Lucidchart for the process map. A shared written pack.
FILTER
Sort what we find into 3 piles: (1) Training or process issue (fix with a one-page checklist), (2) Standard software issue (buy off-the-shelf), or (3) Time spent digging through old files (the only valid build candidate).
DONE
Everyone agrees on today's baseline (e.g. 45 min per quote, $38 cost, 1 in 4 reworked) and picks which task to start with.

STAGE 1WORKING ASSISTANT

A simple question box that proves the pipes work.

BUILD
A clean chat screen. You ask a question, words stream in as they're written, and every request gets logged with how long it took.
USE
Python 3.12+ Ollama (local) / Gemini API Streamlit / Gradio pydantic-settings tenacity structlog pytest
WATCH
Network delays, provider rate limits, and cut-off answers. Settings live in secure environment variables, never hardcoded.
DONE
It runs reliably and an admin can inspect every request.

STAGE 2ANSWERS FROM OUR RECORDS

The assistant looks up past jobs before answering.

BUILD
A search pipeline that reads past job tickets and spreadsheets, finds the closest matches, and gives only the useful parts to the model. Every answer shows its source job number and date.
USE
Docling / pypdf to read PDFs. pandas for spreadsheets. PostgreSQL text search + pgvector. Ragas for answer scoring.
WATCH
Fuzzy scans or missing specs. When the records don't hold the answer, it must say so clearly rather than guessing.
DONE
Every quote claim links to a real job number, and we know which question types it answers reliably.

STAGE 3ACTIONS WITH APPROVAL

Drafts the work, saves it as pending, and waits for a person.

BUILD
Tools such as "find similar jobs" and "draft quote email." The model asks for a tool, our code checks the inputs, and the draft saves in the database under "pending review." The screen shows [Approve], [Edit], [Reject] buttons.
USE
FastAPI Pydantic v2 Model Context Protocol (MCP) Microsoft Graph / Gmail API (drafts emails, never sends).
WATCH
Drafts save straight to the database so nothing is lost if the computer restarts. Unapproved work cannot leave the building.
DONE
It drafts work reliably and a person has the final word on every quote.

STAGE 4MEMORY

Remembers across days and restarts.

BUILD
Database tables for requests, drafts, approvals, sent quotes, and source links. Everything saves as a complete group or not at all.
USE
PostgreSQL SQLAlchemy 2.0 Alembic for safe table updates Pydantic v2
DONE
After a crash, reboot, or overnight shutdown, it knows what is finished and what comes next.

STAGE 5RELIABLE MULTI-STEP WORK

Handles the full job from quote request to sent email.

BUILD
A workflow that looks up past jobs, checks specs, drafts the quote, pauses for you to review, and resumes once approved. If a step hiccups, it retries safely.
USE
LangGraph with PostgreSQL checkpointer to save its place.
WATCH
Work before the pause must be safe to repeat so retries don't send duplicate emails or double-draft work.
DONE
It pauses for hours or days, withstands reboots, and stops at every approval point.

STAGE 6TESTING AND MEASURING

A scorecard that runs after every change.

BUILD
A test set of 20 to 50 real past quote requests, collected since Day 1. Includes tricky cases: conflicting prices, missing papers, and strange requests.
USE
pytest Ragas (answer quality) Langfuse (speed and cost) GitHub Actions
MEASURE
Quote accuracy, citation accuracy, proper tool use, speed, and cost per quote.
DONE
The test suite runs automatically before any code updates, proving the system never gets worse.

Runs safely alongside your shop: Vault only reads past jobs and writes drafts; it cannot modify your live shop software.

5. WHAT COULD GO WRONG & HOW WE HANDLE IT

What Could Happen Why It Happens How the System Protects You
Model slow or temporarily down Internet hiccup or the provider is busy with high traffic. Retries automatically: Tries 3 times with a short pause. If still down, tells the estimator cleanly instead of spinning or freezing.
Made-up prices or specs The model guesses when it can't find an exact match in your files. Must show its sources: Every price must link to a real job number on file. If there is no matching job, it refuses to guess and flags it for human review.
Weird text in customer emails Messy copy/paste or tricky instructions in an incoming RFQ. Strict input checks: Filters strip out weird formatting and commands, only passing clean text and numbers into the system.
Computer reboots while reviewing Nightly system updates or a restart while a draft sits waiting. Saves to the database instantly: Every draft is written to the database the moment it's created. When you log in the next morning, your pending list is right there.
Outdated paper prices Quoting based on a job from two years ago before paper costs went up. Checks dates automatically: The system checks the date on every past job. Anything older than 6 months gets flagged as a stale price.

6. DECIDED IN DISCOVERY

  • Which bottleneck to tackle first: Estimating, reorder spec lookups, scheduling, or paper price books.
  • How past jobs are stored: Clean digital records from your print software or paper job binders that need scanning.
  • Which model provider fits best: Picked under commercial terms that promise never to use your data for training.
  • Where Vault runs: On your company cloud account or on a dedicated PC in the shop.
  • How staff log in: Microsoft 365, Google Workspace, or your existing shop login.
  • How it gets past jobs: A safe read-only copy or a scheduled spreadsheet export from your print software.
